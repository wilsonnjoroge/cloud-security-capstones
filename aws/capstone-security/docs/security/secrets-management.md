# Secrets Management

## Principle

No secret is hardcoded in Terraform configuration, Ansible playbooks, application code, or committed to Git.

Secrets are generated programmatically and stored in AWS Secrets Manager. Secret values must not be written into source files, documentation, shell scripts, or repository history.

Terraform may generate secret values during provisioning, but because generated values can exist in Terraform state, Terraform state is treated as sensitive security material and must be stored securely, encrypted, access-controlled, and excluded from Git.

The application must never receive or require the RDS master credential.

## Secrets Inventory

| Secret                 | Generated by                  | Stored in                                                           | Consumed by                                                                   |
| ---------------------- | ----------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| RDS master credential  | Terraform (`random_password`) | AWS Secrets Manager, encrypted with the dedicated `secrets` KMS key | Initial/bootstrap database administration only; never the running application |
| `app_svc` DB password  | Terraform (`random_password`) | AWS Secrets Manager, encrypted with the dedicated `secrets` KMS key | App-tier IAM role, read-only                                                  |
| ElastiCache AUTH token | Terraform (`random_password`) | AWS Secrets Manager, encrypted with the dedicated `secrets` KMS key | App-tier IAM role, read-only                                                  |

The RDS master credential and `app_svc` credential are separate credentials and separate secret records.

The ElastiCache AUTH token is stored separately from the RDS credentials.

## Application Secret Access

The application receives access only to the secrets it requires.

The app-tier IAM role is permitted to call:

* `secretsmanager:GetSecretValue`
* `secretsmanager:DescribeSecret`

only for the designated:

1. `app_svc` DB credential secret
2. ElastiCache AUTH token secret

The app-tier role must not be permitted to retrieve:

* RDS master credentials
* unrelated application secrets
* other environment secrets
* secrets outside its explicitly assigned scope

The web-tier IAM role has no Secrets Manager read permission.

Secret retrieval occurs over the private AWS service path using the Secrets Manager VPC interface endpoint where applicable.

## RDS Master Credential

The RDS master credential exists for controlled administrative and bootstrap operations only.

It is not:

* embedded in application configuration
* provided to the application IAM role
* used by the running application
* committed to Git
* stored in Ansible playbooks
* exposed through normal application environment variables

The initial database bootstrap process uses the master credential only when required to create/configure the least-privilege `app_svc` database account.

After bootstrap, application database access uses `app_svc`.

The master credential is therefore a break-glass/bootstrap credential rather than an application credential.

## `app_svc` Database Credential

The application uses a dedicated `app_svc` MySQL account.

The account is granted only the permissions required by the application schema and workload.

The password is stored in Secrets Manager and retrieved by the app-tier IAM role.

The database credential is intentionally separate from the RDS master credential so that compromise of the application does not automatically provide the RDS administrative credential.

Creation or synchronization of the `app_svc` database account is performed through the approved bootstrap process rather than exposing database credentials through Terraform-managed database-user resources.

## ElastiCache AUTH Token

The Redis AUTH token is generated independently from the RDS credentials and stored as a dedicated Secrets Manager secret.

The application retrieves the token through its scoped IAM permission.

Redis is configured for:

* TLS/transit encryption
* AUTH
* at-rest encryption
* the dedicated ElastiCache KMS key

The token must never be committed to Git or embedded directly in application source code.

## Terraform State Protection

Terraform-generated secrets can exist in Terraform state even when they are marked sensitive.

Therefore:

* Terraform state must never be committed to Git.
* State files must be excluded through `.gitignore`.
* State storage must be private and access-controlled.
* Remote state should use encryption at rest.
* Access to Terraform state must be limited to authorized infrastructure operators and automation.
* State backups and historical versions must receive equivalent protection.
* Secret values must not be exposed through Terraform outputs.
* Sensitive Terraform outputs must not be printed unnecessarily in CI logs.

The repository's security model therefore distinguishes between:

**Source-code protection**

> No plaintext secret values committed to Git.

and

**State protection**

> Terraform state is sensitive infrastructure data and must be protected accordingly.

## Repository-Level Secret Scanning

Repository scanning provides a second control against accidental secret exposure.

Required controls:

* `.gitleaks.toml` defines repository secret-detection rules.
* Gitleaks runs through the pre-commit workflow.
* Gitleaks also runs in CI.
* Secret scanning covers the current working tree and should also be used when investigating repository history.
* `.env.example` contains only non-secret configuration examples.
* Real `.env` files are Git-ignored.
* `terraform.tfvars.example` contains no credentials or secret values.
* Real `.tfvars` files are Git-ignored.
* Terraform state files are Git-ignored.
* Generated evidence and documentation must not contain secret values.

Git history must be treated as part of the security boundary. A secret accidentally committed and subsequently deleted from the current tree should be considered exposed until appropriately remediated.

## Rotation

Automatic secret rotation is **not currently implemented**.

Secrets Manager supports automatic rotation through a rotation workflow, but this capability is a future implementation item rather than a currently deployed control.

### Current manual rotation model

Manual rotation must update both the stored secret and the actual consumer.

For the RDS `app_svc` credential, the process is:

1. Generate a new password.
2. Update the MySQL `app_svc` account with the new password.
3. Update the corresponding Secrets Manager secret.
4. Restart or refresh the application where required so it obtains the new credential.
5. Validate application database connectivity.
6. Preserve or revoke the previous credential according to the approved rotation procedure.

For the ElastiCache AUTH token, rotation must follow the Redis/ElastiCache-supported credential update process rather than simply changing the Secrets Manager value. The application must then be refreshed with the new token and connectivity validated.

For the RDS master credential, rotation must update the actual RDS master credential and the corresponding Secrets Manager record consistently.

Terraform `random_password` should not be treated as a complete rotation mechanism by itself. Changing the generated value in Terraform does not, by itself, prove that the underlying database or Redis service and all consumers have been synchronized.

## Rotation Cadence

The initial implementation does not define an enforced rotation cadence.

The production implementation must define:

* rotation frequency
* emergency rotation procedure
* ownership
* approval requirements
* rollback procedure
* consumer synchronization procedure
* validation requirements
* handling of old credentials

The cadence should be documented before automatic rotation is introduced.

## Secret Exposure Prevention

Secret values must not appear in:

* Terraform configuration
* Terraform outputs
* Ansible YAML files
* Ansible inventory committed to Git
* shell scripts
* application source code
* Docker/container configuration committed to Git
* `.env` files committed to Git
* CI/CD logs
* screenshots
* architecture diagrams
* validation evidence
* README files or other documentation

Where a secret identifier is required for configuration, use the secret ARN/name rather than the secret value.

## Verification

The following checks must be performed before the implementation is considered validated:

### Repository

* [ ] Confirm Gitleaks runs locally through the pre-commit workflow.
* [ ] Confirm Gitleaks runs in CI.
* [ ] Search Git history for previously committed credentials.
* [ ] Confirm real `.env` files are Git-ignored.
* [ ] Confirm real `.tfvars` files are Git-ignored.
* [ ] Confirm Terraform state files are Git-ignored.
* [ ] Confirm no secret values appear in committed documentation or evidence.

### Terraform

* [ ] Confirm generated passwords are marked sensitive where exposed through Terraform interfaces.
* [ ] Confirm no secret values are exposed through Terraform outputs.
* [ ] Confirm Terraform state is stored securely.
* [ ] Confirm access to Terraform state is restricted.
* [ ] Confirm state encryption is enabled.

### Secrets Manager

* [ ] Confirm the RDS master credential exists as a dedicated secret.
* [ ] Confirm the `app_svc` credential exists as a separate secret.
* [ ] Confirm the Redis AUTH token exists as a separate secret.
* [ ] Confirm secrets use the dedicated `secrets` KMS key.
* [ ] Confirm the web-tier role cannot retrieve secrets.
* [ ] Confirm the app-tier role can retrieve only the two designated application secrets.
* [ ] Confirm the app-tier role cannot retrieve the RDS master credential.
* [ ] Confirm secret retrieval succeeds through the intended private AWS service path.

### Database

* [ ] Confirm `app_svc` can perform only its intended database operations.
* [ ] Confirm the application does not use the RDS master credential.
* [ ] Confirm the master credential is not present in application configuration.
* [ ] Confirm the `app_svc` credential stored in Secrets Manager matches the credential accepted by MySQL.
* [ ] Confirm the application can connect using `app_svc`.

### ElastiCache

* [ ] Confirm the AUTH token is generated and stored separately from RDS credentials.
* [ ] Confirm Redis accepts the configured AUTH token.
* [ ] Confirm the application can authenticate to Redis using the retrieved secret.
* [ ] Confirm Redis transit encryption is enabled.
* [ ] Confirm Redis at-rest encryption is enabled.

### Rotation

* [ ] Document the approved rotation cadence.
* [ ] Document manual rotation procedures.
* [ ] Define automatic rotation as a future implementation.
* [ ] Validate that rotation updates the actual service credential and the corresponding Secrets Manager value.
* [ ] Validate application recovery after credential rotation.

## Validation Status

Controls follow the repository-wide status model:

**Planned → Implemented → Validated**

A control is not marked **Validated** merely because Terraform, Ansible, or documentation declares the control.

Validation requires live evidence where the control depends on deployed AWS resources or actual authorization behavior.

Secret-management evidence must not contain secret values.
